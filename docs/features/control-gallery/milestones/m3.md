## Routing forecast

M3 targets **60–70% accepted local code-bearing lines**. Estimates are recorded in `performance-reports.md` before dispatch; the packet boundaries above intentionally separate shared contracts, public exports, and gallery integration from local control work.

## Choice-control shared invariants

Checkbox, Switch, and RadioGroup implement these rules once rather than inferring them separately in each packet:

- A control is either controlled (`checked`/selected value) or uncontrolled (`defaultChecked`/default value), never both. Its public types reject the conflict and controlled rendering never forwards an uncontrolled default to the native element.
- In uncontrolled use, a native change updates the control's exposed `data-*` state. A native form reset restores both the native control and that exposed state to its default.
- A `Field` requirement reaches the native form element (`required` and `aria-required`); Field continues to own label, help, error, and invalid relationships.
- A `Group` supplies disabled and size state; an explicit child value wins. Native controls retain normal form participation, keyboard behavior, and forwarded refs.
- When a packet lacks a required reusable-control convention, the local agent stops and reports the missing decision. It does not invent an API, state rule, or accessibility behavior. A correction that returns no new commit escalates immediately to the coordinator.

CG-M3-24 through CG-M3-26 own real-browser proof of these invariants for Checkbox, Switch, and RadioGroup respectively.

## CG-M3-04.1 — Conservative Search and feedback contracts

### Shared boundary

- Every control retains applicable Control Base `id`, `size`, disabled, data-state, forwarded-ref, and Field/Group behavior. A public `className`, `style`, or semantic `role` override is rejected in its types and ignored at runtime. Component-owned skin hooks overwrite conflicting consumer `data-*` attributes: `data-control` and `data-tone` have their documented string values; boolean `data-empty`, `data-open`, and `data-loading` use the existing Control Base presence semantics.
- A required behaviour that is not specified below is not inferred. It becomes a later feature question rather than a local-agent workaround. The source packets do not add CSS outside their own directory; CG-M3-04.2 owns shared default-skin rules.

### CG-M3-05 — Search

- **API and entry:** `Search` is one native `input type="search"` with `value` or `defaultValue`, `onValueChange`, optional `onClear`, and normal native search-input attributes except native `onChange`, which is omitted in favour of `onValueChange`. `value` and `defaultValue` are mutually exclusive. The ref targets the native input; it exposes `data-control="search"` and presence-style `data-empty`; `Field` supplies its label, help/error relationships, inherited disabled/size, and required state.
- **State and recovery:** An uncontrolled query updates `data-empty` and restores both its native value and `data-empty` after native form reset. A controlled query reports changes but never mutates its own displayed source of truth. Typing calls `onValueChange(nextValue)` once after the internal uncontrolled state update, or once without a state update in controlled mode. A clear button exists only for a non-empty, effectively enabled query; it is native `type="button"`, sends `onValueChange('')` once followed by `onClear()` once, and returns focus to the input. Reset fires neither callback; disabled input and clear action refuse changes.
- **Scope boundary:** Search does not render suggestions, a popup, a result list, remote requests, debouncing, filtering policy, or a search landmark. Its gallery example filters a fixed local list, renders empty/match/no-match content, and updates one `role="status" aria-atomic="true"` result summary. Form submission remains native consumer behavior.
- **Validation:** Component checks cover native type/ref, controlled/default conflict, Field requirement/wiring, uncontrolled input/clear/reset, disabled behaviour, component-owned hook override/type/runtime refusal, and no added result widget. CG-M3-15 and CG-M3-27 own visible results and live-browser proof.

### CG-M3-06 — StatusChip

- **API and entry:** `StatusChip` receives required visible `label` and `tone` (`neutral`, `success`, `warning`, or `danger`, default `neutral`). It renders one non-focusable `span` with fixed `role="status"`, `aria-atomic="true"`, `data-control="status-chip"`, `data-tone`, and applicable size state; the ref targets that span.
- **State and refusal:** It communicates outcome in text as well as tone. It has no dismiss, loading, link, action, or automatic timer behavior; an urgent interactive response belongs to Banner or a later Dialog. Consumer semantic/styling escapes are refused.
- **Validation:** Component checks cover every tone, visible label, polite status semantics, no keyboard target, ref/type/runtime boundary including component-owned hook override, long label, and adjacent-chip behaviour. CG-M3-16 and CG-M3-28 own gallery and browser proof.

### CG-M3-07 — Banner

- **API and entry:** `Banner` receives required `title`, required `description`, `tone` (`neutral`, `success`, `warning`, or `danger`), optional recovery `action`, and controlled or uncontrolled `open`/`defaultOpen` plus `onOpenChange`. It renders a labelled semantic `section` with `data-control="banner"`, `data-tone`, and Control Base presence-style `data-open`; its visible title is the accessible name and description is present as text.
- **State and recovery:** `open` and `defaultOpen` conflict. An initially or subsequently closed banner renders nothing. A dismiss button appears only when `onOpenChange` is provided, uses the catalogue `dismiss` label, reports `false` once, and does not move focus. A controlled parent can restore it by returning `open` to true. An uncontrolled dismissal remains closed for that mounted instance; its only supported restoration is a deliberate remount with a new `defaultOpen` value. Banner never auto-dismisses and never uses ARIA `banner` or `alert`, because it may contain a Button recovery action.
- **Validation:** Component checks cover tones/text, controlled/uncontrolled open and conflict refusal, dismiss/restore, action presence, fixed semantics, long content, and public-boundary/component-hook override refusal. CG-M3-17 and CG-M3-29 own gallery and browser proof.

### CG-M3-08 — Toast

- **API and entry:** `Toast` receives required `title`, optional `description`, `tone` (`neutral`, `success`, or `warning`), controlled or uncontrolled `open`/`defaultOpen`, and optional `onOpenChange`. One rendered toast is one native labelled section with `data-control="toast"`, `data-tone`, and Control Base presence-style `data-open`; its message element is fixed `role="status" aria-atomic="true"`. A close Button exists only when `onOpenChange` is provided and is outside that live-message element.
- **Lifecycle and refusal:** `open` and `defaultOpen` conflict. Core v1 has no provider, queue, portal, stacking, hover-pause, timeout, or auto-dismiss behavior: a caller renders at most one toast and replaces its content rather than appending duplicates. Close reports `false` once without moving focus. A controlled parent can reopen by returning `open` to true; an uncontrolled dismissal remains closed for that mounted instance and can only reopen through a deliberate remount with a new `defaultOpen` value. Critical/danger messages use persistent Banner or a later blocking pattern, not an assertive interactive toast.
- **Validation:** Component checks cover polite announcement semantics, controlled/uncontrolled close/reopen, conflict refusal, one-toast boundary, no auto timer, no focus move, and public-boundary/component-hook override refusal. CG-M3-18 and CG-M3-30 own gallery and browser proof.

### CG-M3-09 — EmptyState

- **API and entry:** `EmptyState` receives required `title`, required `description`, and optional recovery `action`. It renders one labelled semantic `section` with `data-control="empty-state"`; the forwarded ref targets that section.
- **State and refusal:** It is presentationally stable rather than live, dismissible, or loading. It provides visible recovery text and may contain the one supplied recovery action; no result count, automatic navigation, or consumer styling escape is introduced.
- **Validation:** Component checks cover semantic title/description linkage, zero/one supplied action, long content, ref/type/runtime boundary including component-owned hook override, and adjacent-flow behaviour. CG-M3-19 and CG-M3-31 own gallery and browser proof.

### CG-M3-10 — LoadingSkeleton

- **API and entry:** `LoadingSkeleton` receives required accessible `label`, optional `lines` from 1 through 6 (default 3), and applicable size state. It renders one non-focusable busy status with `aria-busy="true"`, `role="status"`, `data-control="loading-skeleton"`, and Control Base presence-style `data-loading`; every visual bar carries `data-skeleton-bar` and is `aria-hidden`. The forwarded ref targets the status root.
- **State and refusal:** The component's presence means loading; it has no false state, percentage, progressbar role, timer, or content fetch. Invalid line counts refuse before rendering. The default skin supplies any non-essential shimmer only under no-reduced-motion conditions, while the existing gallery motion setting suppresses it as well.
- **Validation:** Component checks cover labelled busy semantics, 1/3/6 lines and invalid refusal, hidden visual bars, size/ref/type/runtime boundary including component-owned hook override, and reduced-motion selector presence. CG-M3-20 and CG-M3-32 own gallery and browser proof.

## CG-M3-04 — RadioGroup contract

- API: `RadioGroup` receives `name`, `options`, optional `value` or `defaultValue`, `onValueChange`, and the applicable Control Base properties. An option is `{ value, label, disabled? }`. `value` and `defaultValue` are mutually exclusive; consumer `className`, `style`, and semantic-role overrides are forbidden.
- Entry and empty state: the root is one native `fieldset` with `aria-labelledby` and `aria-describedby` set from the Field context; it does not rely on Field's HTML `label for` association because a fieldset is not labelable that way. Each option's own visible `label` labels its native radio. An empty option list renders that labelled group with no radios and no selection; a duplicate option value is refused before rendering rather than creating an ambiguous native form value.
- Selection: controlled mode exposes the supplied value and reports user selection through `onValueChange`; uncontrolled mode stores its own selected value. A required uncontrolled group with no default selects its first enabled option so the required invariant holds. A supplied value that does not match an option renders no selected option and does not invent a replacement only when the group is not required.
- Required refusal: a required group refuses before rendering when it has no enabled option, or when its controlled `value` or a supplied uncontrolled `defaultValue` is absent from the enabled options. An omitted uncontrolled default selects the first enabled option. Its fieldset exposes `aria-required`; its first enabled native radio exposes both native `required` and `aria-required`. A non-required empty, all-disabled, or missing-value group renders with no selection.
- Form and recovery: each option is a native same-name radio input. A native form reset restores the uncontrolled selected value to its default (or the required initial option). Disabled options cannot be selected. `RadioGroup disabled={false}` overrides disabled state inherited from Field or Group; after the RadioGroup's effective disabled state is true, every option is disabled and an option-level `disabled: false` cannot re-enable it.
- Keyboard: ArrowLeft/ArrowUp and ArrowRight/ArrowDown move selection and focus among enabled options with wraparound; Home and End move to the first and last enabled option. Pointer activation follows the same selection path. No enabled option means keyboard movement is a no-op.
- Refusal and validation: required groups retain exactly one selected enabled option after every internal transition. The forwarded ref targets the native fieldset. Component tests cover value/default conflict, duplicate and empty options, controlled/uncontrolled selection, required initial selection, disabled options/group, Field relationships, keyboard-target calculation, reset wiring, and type boundaries. CG-M3-26 owns live-browser keyboard and reset proof.

## CG-M3-01 — Button contract

- Entry: `Button` renders one native `button` with a required label category. It resolves the displayed label through `LocaleProvider`; a supplied label changes only the approved `add` or `back` categories.
- State: `variant` is one of Primary, Secondary, Destructive, or Link and defaults to Primary. Calling code maps its own domain state to the existing `variant`, `disabled`, and `loading` props; Foundry does not introduce a product-specific state enum.
- Refusal: disabled and loading buttons render as native disabled controls and do not invoke their action. Loading exposes `aria-busy` and `data-loading`; return to an enabled, non-loading prop state restores normal activation.
- Contract: the ref targets the native button. `id`, `size`, `invalid`, `disabled`, `loading`, and pass-through `data-*` values follow Control Base. Consumer `className` and `style` remain forbidden.
- Validation: component checks cover category resolution, the four variants, locked-label refusal, loading/disabled state attributes, native ref/type boundary, and default native-button type. Gallery and browser behavior remain CG-M3-11 and CG-M3-23.

## Acceptance criteria

- Button variants are visually distinct and invoke their expected gallery behavior.
- Disabled/loading buttons cannot submit or duplicate an action.
- Checkboxes, switches, and radio groups work with pointer and keyboard input and reset correctly.
- Search has empty, matching, and no-match states.
- Toasts announce, banners can be dismissed/restored, and loading/empty states are observable.

## Invariants

- A radio group has one selected value when it is required.
- Feedback text gives an outcome or recovery, not only a color signal.
- Repeated activation cannot create an unbounded duplicate action.
